# Sessions wiki format (format_version 1)

The wiki is a set of Markdown documents **optimized for LLM consumption, not human readability**. Structure is rigid so that scripts and other skills (search-sessions-wiki, interrogate-sessions, session-retro) can parse it deterministically.

## Directory layout

```
<wiki-root>/
  wiki-meta.json        # machine-written: last_refreshed, format_version, page_count
  INDEX.md              # machine-generated master index (one line per session)
  tags/
    TAGS.md             # machine-generated tag -> sessions cross-reference
  sessions/
    <project-dir-name>/
      <session-id>.md   # one page per session (LLM-written body, strict frontmatter)
```

`INDEX.md`, `tags/TAGS.md`, and `wiki-meta.json` are regenerated by `wiki_tools.py finalize` — never hand-edit them; edits are overwritten. Session pages are the source of truth the index is rebuilt from.

## wiki-meta.json

```json
{
  "created_at": "<ISO>",
  "format_version": 1,
  "last_refreshed": "<ISO — the START time of the most recent refresh run>",
  "last_refresh_machine": "<hostname>",
  "last_refresh_finished_at": "<ISO>",
  "page_count": 42
}
```

`last_refreshed` is deliberately the refresh run's **start** time: any session modified while the refresh was running falls after it and gets picked up by the next incremental run. It is also echoed in the `INDEX.md` header.

## Session page frontmatter (strict)

Flat `key: value` lines between `---` delimiters. No nesting, no YAML lists — `tags` is a comma-separated string. `wiki_tools.py` parses this with a minimal parser; any deviation makes the page invisible to `plan`/`finalize`.

```
---
session_id: <uuid — must equal the source .jsonl basename>
project: <munged project dir name, e.g. c--sourcecode-github-Daily>
machine: <hostname that indexed it, from the metrics JSON "machine" field>
source_path: <absolute path of the session .jsonl on that machine>
source_mtime: <ISO, human-readable copy of the mtime>
source_mtime_epoch: <int — from metrics "source_mtime_epoch">
source_size: <int — from metrics "source_size" (main + subagent files combined)>
first_ts: <ISO of first assistant activity>
last_ts: <ISO of last assistant activity>
indexed_at: <ISO when this page was written>
title: <one line, LLM-written>
tags: <comma-separated, lowercase-kebab, LLM-written>
cwd: <working directory of the session>
git_branch: <branch, or empty>
---
```

**The fully-indexed fingerprint.** `machine` + `source_mtime_epoch` + `source_size` is how `plan` decides a page is current: if all three match the live file set (main JSONL + subagent transcripts), status is `unchanged` and the page is considered **fully indexed** — downstream skills (including session-retro) may trust it instead of re-reading the raw JSONL. Any mismatch → `changed` → the page must be rebuilt.

The fingerprint and the `## Metrics` block are both produced by `scripts/session_core.py`, the single shared parser that `wiki_tools.py` and session-retro's `parse_sessions.py` both import. There is no second implementation to keep in sync — change parsing/fingerprint behavior in `session_core.py` only, and `tests/test_contract.py` guards the coupling.

## Session page body sections (in order)

1. `## Summary` — LLM-written work summary: what was asked, what was done, key decisions, files touched.
2. `## Outcome` — LLM-written: how the session ended (completed / abandoned / handed off), the **last step taken and its result**, and any errors or unresolved items. This section exists specifically so "what was the last step and what happened" questions are answerable without re-reading transcripts.
3. `## Prompts (verbatim, N total)` — pasted **unmodified** from `wiki_tools.py prompts` output. Original user prompts with timestamps; long prompts carry an explicit truncation marker.
4. `## Keywords and cross-references` — LLM-written: keyword list beyond the frontmatter tags, plus links to related session pages (`sessions/<project>/<id>.md`) and why they relate (same task continued, same bug, same project phase).
5. `## Metrics (machine-generated, pricing-free)` — a fenced ```json block containing the **verbatim** output of `wiki_tools.py metrics`. Never edit or summarize this JSON; session-retro consumes it (token buckets per model incl. sidechain, gap events, repeat reads, large tool results, context growth, tool-use counts, flags). It is pricing-free by design — dollar figures are always computed later by whoever reads it, using current rates.

## Multi-machine and aged-out sessions

The wiki may legitimately contain more sessions than exist locally: sessions age out of `~/.claude/projects`, and a source-controlled wiki may hold pages indexed on other machines. Therefore:

- **Never delete or prune a session page** because its source file is missing locally.
- `plan` reports such pages only as a `wiki_only_sessions` count, never as work items.
- A page whose `machine` differs from the current hostname is never treated as `unchanged` for local rebuild decisions, but its content remains valid history and stays in the index.

## Source control

The wiki folder may be a git repo (or inside one). The skills **never** run `git add`/`commit`/`push`/`pull` there and never resolve merge conflicts. All source control is the user's responsibility.

## Tagging conventions (for the LLM-written `tags` field)

- lowercase-kebab-case, 3–10 tags per session.
- Include: the human project name (e.g. `daily`, `claude-skills`), major tools/skills used (`ralph`, `session-retro`, `create-plan`), the task domain (`fact-checking`, `substack`, `wiki`), and notable event types (`debugging`, `refactor`, `abandoned`, `error-loop`).
- Reuse existing tags where possible — check `tags/TAGS.md` before inventing a near-duplicate (`fact-check` vs `fact-checking`).
